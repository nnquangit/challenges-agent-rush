ProofBox

How it works

One request from plan to signed receipt, with the code that does each step.

Mock build. No container or VM runs, and the app makes no calls to Vultr or any other external service. Results such as "blocked", "OOM-killed" and "destroyed" come from software rules in MockSandbox; they are not evidence of real isolation.

Big picture

A request goes through three stages. Plan: the LLM proposes steps and the server validates and rewrites them. Dispatch: each step, and each retry, gets a fresh sandbox that is always destroyed. Receipt: scrubbed output plus an isolation report, sealed with sha256 and Ed25519. Browser actions with side effects wait for a human. In this build the LLM and the sandbox are mocks (dashed).

Interactive versions: sequence of a run, human confirm gate and step status lifecycle (all on Diagrams).

Step by step

One run of the Prove-It Python preset, in the order the code runs it. The diagram above the list walks through the steps on its own.

  1. Start a session — on load the UI reads /api/status and posts /api/session (src/components/ProofBoxApp.tsx:openSession). src/app/api/session/route.ts:POST mints a random principal and sets the HttpOnly cookie pb_session signed by src/lib/access.ts:signSession. With a token configured, the UI asks for it first.
  2. Ask for a plan — clicking a preset posts its message (src/components/ProofBoxApp.tsx:send). src/app/api/chat/route.ts:POST calls requireSession (401 without a valid cookie), applies the per-principal limit, and requires message (400 if missing, 413 over 20000 characters).
  3. Plan — src/lib/llm/index.ts:getLlm returns MockLlm; src/lib/llm/mock-llm.ts:MockLlm.plan classifies the intent (code, csv, browser) and returns template plan JSON. Simulated.
  4. Plan JSON — one step, "Run code in sandbox", with the user's Python.
  5. Policy — src/lib/policy.ts:enforcePolicy runs validatePlan (at most 8 planner steps, kinds code/browser, http(s) URLs, code up to 20000 characters), clears probe flags set by the LLM, forces requiresConfirm on submit, sets egress to userHosts(message) ∩ SANDBOX_EGRESS_ALLOWLIST, and appends the standard probes (addedBy: "policy") before the first gated step. Here: Containment probe and Resource cap probe, 3 steps in total.
  6. Plan shown — src/lib/store.ts:savePlan keeps the plan in memory with owner = the caller's principal; the route answers { reply, plan }.
  7. Dispatch — Dispatch to sandbox → posts { planId }. src/app/api/runs/route.ts:POST accepts only the caller's own stored plan (ownPlan; 404 otherwise) and answers 202.
  8. Start the run — src/lib/orchestrator.ts:startRun refuses a used plan (409, plans are single-use) or a caller with 2 active runs (429), creates the run with the same owner and calls advance, which locks it (store.locks) and walks the steps. A step needing confirmation stops at awaiting_confirm before any sandbox is created; the orchestrator re-checks submit itself, independent of the planner.
  9. Run one step — orchestrator.ts:executeStep → src/lib/sandbox/index.ts:runInSandbox: a slot from the fair SlotPool (src/lib/sandbox/slots.ts: global cap, per-principal share, round-robin, bounded wait), buildSandboxEnv, clamp egress to the server allowlist again, then create → exec → artifacts → redactText → destroy() in finally.
  10. Seal — the isolation report is read after destroy(), then src/lib/sandbox/signing.ts:sealReceipt hashes and signs the canonical JSON of the whole receipt (src/lib/receipt-canonical.ts).
  11. Receipt back — exit 0: the step succeeds. A probe succeeds only if something was blocked or a cap killed it.
  12. Explain — code failure (not a probe): llm.repair() and at most one retry (MAX_ATTEMPTS = 2); browser step: llm.verify(); every step: llm.explain(). All template answers in mock mode.
  13. Poll — while the run is live the UI polls src/app/api/runs/[id]/route.ts:GET every 450 ms; only the owner's session gets the run (ownRun), anyone else 404.
  14. Done — the chat shows "Run succeeded: 3/3 steps succeeded"; each receipt carries the badge CONTAINED (SIMULATED).

For a browser plan with a submit step, src/app/api/runs/[id]/confirm/route.ts → orchestrator.ts:confirmStep resumes the run — only for the run's owner (404 for anyone else) and only once (409 for a replay or a duplicate): approve runs the step, deny marks it skipped with no sandbox attempt. An unanswered gate is denied after CONFIRM_TTL_MS (10 min). Run again in the UI asks the planner again, because a plan can be dispatched only once.

Failure paths

  • No session, wrong host or origin: 401 session_required; 403 for a non-loopback Host in local mode or a cross-origin POST; 503 when the security config is invalid (src/lib/access.ts:precheck).
  • Bad input: missing message or invalid JSON → 400; over 20000 characters → 413 (src/app/api/chat/route.ts).
  • Invalid plan from the planner: validatePlan throws PlanRejected → 502; nothing runs.
  • Unknown or foreign planId → 404; a plan dispatched before → 409; too many active runs → 429. An unknown or foreign run → 404; confirming a step that is not waiting → 409.
  • Code failure (exit ≠ 0, not a probe): one repair attempt. An AssertionError is not repaired: a disproven claim is recorded as failed (src/lib/llm/mock-llm.ts:repair).
  • Time or memory cap: the mock returns killedBy: "timeout" (exit 124) or "memory" (exit 137) on a simulated clock.
  • Probe not blocked: the probe step fails and the timeline says "Probe was not blocked!".
  • All sandbox slots busy: runs and ad-hoc execs wait in a bounded per-principal queue and are served round-robin; a full queue or a wait longer than SANDBOX_EXEC_WAIT_MS (exec) → 429, longer than SANDBOX_RUN_WAIT_MS (run step) → the run aborts (src/lib/sandbox/slots.ts:acquire).
  • Nobody answers the gate: after CONFIRM_TTL_MS the step is denied (confirm.expired) and the run finishes without the submit.
  • Provider error (for example MOCK=0 with the stubs): the slot is released, the running step and the run become failed, and the timeline says "Run aborted: …".
