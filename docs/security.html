Security

What ProofBox protects, how, and what is not protected yet.

Mock build. No container or VM runs, and the app makes no calls to Vultr or any other external service. Results such as "blocked", "OOM-killed" and "destroyed" come from software rules in MockSandbox; they are not evidence of real isolation.

Assets and trust boundaries

Protected: host secrets (Vultr and app keys), the host machine and its network (cloud metadata, loopback, private ranges), compute budget (sandbox slots), each user's runs and the human decision on them, user data passed into runs (messages, CSV files), and the integrity of receipts.

Who the caller is: the session principal — a random id the server puts in an HttpOnly, SameSite=Strict, HMAC-signed cookie (pb_session) from POST /api/session. Plans and runs record that principal as owner; list, read, dispatch and confirm only ever reach the caller's own objects. The optional access token (PROOFBOX_DEMO_TOKEN) only lets a caller start a session; it is never an identity, and client-supplied headers such as x-forwarded-for are not an identity either.

Untrusted inputs: the LLM's plan (it can be wrong, or prompt-injected by pages and data it reads), every HTTP request (body, headers, Host, Origin, cookies), and anything the sandboxed code or browser produces. Safety therefore lives in server code (access checks, policy, orchestrator, runInSandbox), not in the model's output or the UI.

Exposure modes: local (default) answers only requests whose Host is loopback; public (PROOFBOX_PUBLIC=1) accepts any host but refuses to start without the token and a stable signing key.

In this build the sandbox boundary is simulated: MockSandbox does not execute user code, so no kernel, container or VM tests the host-isolation claims. Mock unit tests prove the rules, never real isolation.

Secrets handling

  • Secrets are supplied only as environment variables: VULTR_INFERENCE_API_KEY, VULTR_SANDBOX_TOKEN, VULTR_API_KEY, PROOFBOX_DEMO_TOKEN, PROOFBOX_SESSION_SECRET, RECEIPT_SIGNING_KEY. .env.example lists the names with empty values; no secret is needed in local mock mode.
  • The access token is compared in constant time and only on POST /api/session; the browser keeps it in memory, never in storage. The session cookie is HttpOnly, so page scripts cannot read it.
  • PROOFBOX_SESSION_SECRET (at least 32 characters) signs session cookies; unset = a random secret per process, so sessions end on restart, like the in-memory runs they own.
  • Inside a sandbox only LANG, TZ and a fixed HOME/USER/PATH are forwarded; scoped secrets appear as [REDACTED]; every other host variable is dropped.
  • Mock mode adds a public, fake canary key on the host so the demo can show redaction; it is not a secret (src/lib/sandbox/index.ts:13-14).
  • Signing key: RECEIPT_SIGNING_KEY is a base64 PKCS#8 DER Ed25519 private key, validated at start. Use one stable key per deployment (generate it once with the command in .env.example, store it outside the repository) so receipts keep verifying after restarts; public mode requires it. Without it an ephemeral key is generated per process ("ephemeral": true). The signature proves a receipt was not changed after sealing; it does not prove the server told the truth when sealing.
  • Startup and error messages name variables, never values. Never put keys in the repository, logs, screenshots or the client bundle.
