Security

What ProofBox protects, how, and what is not protected yet.

Mock build. No container or VM runs, and the app makes no calls to Vultr or any other external service. Results such as "blocked", "OOM-killed" and "destroyed" come from software rules in MockSandbox; they are not evidence of real isolation.

Assets and trust boundaries

Protected: host secrets (Vultr and app keys), the host machine and its network (cloud metadata, loopback, private ranges), compute budget, user data passed into runs (messages, CSV files), and the integrity of receipts.

Untrusted inputs: the LLM's plan (it can be wrong, or prompt-injected by pages and data it reads), every HTTP request body, and anything the sandboxed code or browser produces. Safety therefore lives in server code (policy, orchestrator, runInSandbox), not in the model's output.

In this build the sandbox boundary is simulated: MockSandbox does not execute user code, so no kernel, container or VM tests the host-isolation claims. Mock unit tests prove the rules, never real isolation.

Secrets handling

  • Secrets are supplied only as environment variables: VULTR_INFERENCE_API_KEY, VULTR_SANDBOX_TOKEN, VULTR_API_KEY, PROOFBOX_DEMO_TOKEN, RECEIPT_SIGNING_KEY. .env.example lists the names with empty values; no secret is needed in mock mode.
  • Inside a sandbox only LANG, TZ and a fixed HOME/USER/PATH are forwarded; scoped secrets appear as [REDACTED]; every other host variable is dropped.
  • Mock mode adds a public, fake canary key on the host so the demo can show redaction; it is not a secret (src/lib/sandbox/index.ts:12-13).
  • Signing key: without RECEIPT_SIGNING_KEY an ephemeral Ed25519 key is generated per process (/api/receipts/public-key reports "ephemeral": true), so receipts from before a restart no longer match the published key. The signature proves a receipt was not changed after sealing; it does not prove the server told the truth when sealing.
  • Never put keys in the repository, logs, screenshots or the client bundle.
