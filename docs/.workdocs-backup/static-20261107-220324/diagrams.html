Architecture (current code)

Work map: Epic 5 Product, P6 Control plane, P10 LLM, P11 Sandbox (diagram task T7)

The browser UI calls the API routes; POST /api/chat plans and applies the policy, POST /api/runs starts the orchestrator, and runInSandbox() is the only way code reaches a sandbox. getLlm() and getSandboxProvider() pick the mocks while MOCK=1.

Source: src/app/api/*, src/lib/orchestrator.ts, src/lib/sandbox/index.ts:runInSandbox, src/lib/llm/index.ts:getLlm

Plan, then run each step in its own sandbox

Work map: P6 Control plane, P7 API (T11, T14)

Sequence diagram. Planning runs nothing: the chat route asks the planner, applies enforcePolicy() and stores the plan. A run is started from a stored planId; for every step the orchestrator calls runInSandbox(), which creates, executes, collects artifacts, destroys the sandbox in finally and seals the receipt. The UI polls the run every 450 ms.

Source: src/app/api/chat/route.ts:POST, src/lib/policy.ts:enforcePolicy, src/app/api/runs/route.ts:POST, src/lib/orchestrator.ts:startRun, src/lib/orchestrator.ts:executeStep, src/lib/sandbox/index.ts:runInSandbox, src/components/ProofBoxApp.tsx (poll)

Human confirm gate

Work map: P6 Control plane (T12 Human confirm)

Sequence diagram. Before a step with side effects (every browser submit), the run pauses at awaiting_confirm and the dialog opens with Deny focused. Approve resumes the run and the submit step runs in a fresh simulated sandbox; Deny marks the step skipped and nothing is submitted.

Source: src/lib/orchestrator.ts:advance, src/lib/orchestrator.ts:confirmStep, src/app/api/runs/[id]/confirm/route.ts:POST, src/components/ConfirmDialog.tsx

Step status lifecycle

Work map: P6 Control plane

Lifecycle diagram of StepStatus: pending, running, awaiting_confirm, succeeded, failed, skipped. A failed code step is repaired once by llm.repair() while it stays running (MAX_ATTEMPTS = 2). The run status (RunStatus) is summarised in the diagram's cards.

Source: src/lib/types.ts (StepStatus, RunStatus), src/lib/orchestrator.ts:advance, src/lib/orchestrator.ts:executeStep

Control-plane policy

Work map: P15 Control-plane rules (T29, T30)

Workflow diagram. Every plan from any planner goes through validatePlan(), then the server clears planner-set probe flags, forces a confirm on every browser submit, inserts its own probes before the first gated step and sets the egress allowlist to hosts the user typed that are also on the server list. At run time the orchestrator and runInSandbox() check again. The blocks themselves are enforced by MockSandbox rules (simulated).

Source: src/lib/policy.ts:validatePlan, src/lib/policy.ts:enforcePolicy, src/lib/policy.ts:userHosts, src/lib/orchestrator.ts:advance, src/lib/sandbox/index.ts:runInSandbox

Receipt pipeline

Work map: P16 Verifiable receipts (T31, T32)

Data-flow diagram. Sandbox output is scrubbed by redactText(), combined with limits, env, timestamps and the isolation report read after destroy(), turned into sorted-key JSON by receiptPayload(), and sealed with sha256 + Ed25519. The browser and scripts/verify-receipt.mjs recompute the same bytes. A valid signature proves the receipt was not edited; in mock mode the isolation report is still simulated.

Source: src/lib/sandbox/redact.ts:redactText, src/lib/sandbox/index.ts:runInSandbox, src/lib/receipt-canonical.ts:receiptPayload, src/lib/sandbox/signing.ts:sealReceipt, src/components/ReceiptViewer.tsx:verifyReceipt, scripts/verify-receipt.mjs
